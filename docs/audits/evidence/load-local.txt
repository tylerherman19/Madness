######## What this does and does not show
- Findings: on this laptop ONE Next production process (one Node thread) is saturated (~100-110% CPU, ~14 req/s at 50 visitors, ~47 req/s offered at 250) before the database is: Postgres averaged 1.5-5 ms per query and the pool (10) was never the limit for viewing; in the pick rush the adapter pool queue grew (max waiting 400-850) but p50 submit latency tracked Next CPU, not query time. From 250 visitors up, most failures are connection resets/EPIPE from the saturated listener (client-side symptoms of overload), not application errors; the application itself returned no 5xx. After the load stopped, health and home recovered immediately (home ~35 ms).
- Pick rush: every accepted (HTTP 200) pick was in the database; no duplicates; the third run, with the lock moving mid-run, accepted no pick after the lock (0 rows with updated_at after the lock; 127 refused with the locked message). Picks whose response was lost to a reset/timeout were sometimes saved anyway (5-45 per run); the app's request-id reconciliation exists for that, but this script did not retry.
- Not the production stack: a single laptop shared with other work (load average 5-29 during runs, iCloud daemons above 100% CPU), local PostgreSQL, a fake PostgREST adapter in a Node process, a load generator on the same machine, no Vercel functions (which scale horizontally per request), no Supabase API gateway, Free-tier connection/CPU limits or rate limits. The adapter pool has no acquire timeout, so overload shows as latency rather than PostgREST 504s. Cookies were minted, not logged in. 15 ms added latency approximates a remote database but not its variance. Local success or failure therefore does not prove or disprove production capacity; the numbers are useful for comparing code changes on the same machine and for finding which tier saturates first (here the Node render path).
- Not done in this run: no code change to pickWindow/picks route (the database was not the bottleneck, so removing reads would not have been supported by the evidence); 500-visitor stage was run but 50/100 stages ran with a different HTTP client (fetch) than 250+ (node:http) after the first crashed with an undici socket error.
