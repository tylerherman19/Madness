# Pick and Pray deployment checks

- Set `NEXT_PUBLIC_APP_URL` to the primary HTTPS domain before building. Metadata, canonicals and sitemap entries use that origin (default: `https://madness-cyan.vercel.app`). Redirect alternate production domains to that primary domain in Vercel to avoid duplicate content.
- `NEXT_PUBLIC_SUPPORT_EMAIL` can override the existing `pool@pickandpray.org` contact. Confirm it reaches the organizer. Fee/payment copy follows the current $25 / @griffinsell pool. Confirm and update refund/payout details before accepting payments if the organizer has different policies.
- Enable Web Analytics in the Vercel project dashboard. The integration is installed, uses no analytics cookies, excludes account/admin/API pages, and strips query strings and fragments. This repository has no advertising trackers; adding tracking that requires consent also requires a consent flow and a privacy-policy update.
- Vercel enforces HTTPS for hosted deployments; the app adds HSTS and upgrades insecure subresources in production. CSP allows inline scripts required by Next.js hydration and inline styles used by the existing UI. Production excludes `unsafe-eval`. A stricter nonce policy would require converting the existing static/ISR pages to per-request rendering.
- Monitor `GET /api/health` from an external uptime service. A 200 means the server and a read-only database query succeeded; 503 means database access/configuration failed or timed out. GitHub Actions also checks public uptime and, with MONITOR_SECRET configured, job freshness; failure notifications follow the repository notification settings. Vercel runtime logs retain server errors; error screens let players retry or reach the organizer.
- Existing authenticated exports: `/api/admin/export?type=players` and `/api/admin/export?type=picks`, accessible from the admin UI. They are CSV exports, not full restorable backups. Use Supabase backups/point-in-time recovery according to the project plan; download a verified database backup before destructive operations. Store exports securely because they contain personal information. The encrypted nightly application backup, its private storage, and the restore procedure are in [backup-recovery.md](backup-recovery.md); it must be configured and verified separately from provider backups.
- All API mutations reject mismatched browser Origins and pass the proxy limiter: a signed-in player has a personal 120/minute write budget, anonymous writes share 600/minute per address, and every address keeps a 1,200/minute ceiling. Login is limited per account per address (10/15 min), per account from anywhere (30/15 min) and per address (1,000/15 min); a throttled key stops evaluation, so one abusive client on a campus or office network does not use up the budget everyone else on it shares. Keys and budgets live in `src/lib/rateLimitPolicy.ts`. Admin login and signup limits are unchanged.
- `SESSION_SECRET` must be at least 32 random characters in production (`openssl rand -base64 32`); short or placeholder values are refused per request (sign-in returns 503 and existing sessions read as signed out) while the build still succeeds. `SESSION_SECRET_ENFORCEMENT=warn` temporarily logs instead of refusing; remove it after rotating. Rotating the secret signs everyone out once.
- Password recovery has no email: the organizer opens Admin → Players → Manage → Reset Link, which shows a one-time link (valid 60 minutes, shown once, never stored) to pass on directly. A newer link cancels the older one; using it changes the password and signs that player out everywhere. Creation, use, expired and reused links are in the audit log. Supabase's atomic limiter shares counts across instances; an outage falls back to bounded process-local budgets, which cannot share limits across instances.
- Validate with `npm ci`, `npm test`, `npm run lint`, `npm run build`, then `npm start`. Check the legal pages, signup consent, mobile navigation/footer, social image, sitemap, robots, and a nonexistent route. Use a physical phone for a final device check; browser emulation is not a physical device test.

Operational worker, backup/restore, retention, monitoring activation and rollback: see [automation-release.md](automation-release.md). No MFA or enterprise features are required for this rollout.
